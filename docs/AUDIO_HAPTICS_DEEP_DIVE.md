## 引言：为什么你能"感受到"爆炸？

你正在用手机串流一款 3A 大作。角色推开一扇门，背后是一场剧烈的爆炸——你的手掌感受到一阵沉闷的震颤，就像冲击波穿过了屏幕。进入下一个场景，背景音乐切换到一首紧张的鼓点配乐，你的设备开始随着每一声底鼓的敲击产生清晰的脉冲。

## 第一章：触觉反馈简史 —— 从偏心转子到线性马达

### 1.1 ERM：最朴素的震动

1997 年，任天堂在 N64 手柄上推出了 **Rumble Pak**，内部是一个 **ERM（Eccentric Rotating Mass，偏心旋转质量）** 马达 —— 一个小电机带动不对称的金属块旋转，产生离心力引起振动。

ERM 的特点：
- **便宜**（成本几毛钱）
- **响应慢**（启停需要 ~50-100ms，转子有惯性）
- **频率不可控**（转速决定频率，振幅和频率耦合在一起）
- **只有一种感觉**：嗡嗡嗡

> 你手机里的老式振动马达，和 20 年前的游戏手柄用的是同一种原理。

### 1.2 LRA：精确的心跳

2015 年，Apple 在 iPhone 6s 中引入了 **Taptic Engine**，核心是 **LRA（Linear Resonant Actuator，线性谐振致动器）**。它的工作原理类似一个微型扬声器：电磁线圈驱动一个质量块做直线往复运动（而不是旋转）。

LRA 的优势：
- **响应快**（启停 ~5-10ms）
- **频率可控**（通常谐振在 150-250Hz，可以通过驱动信号精确控制）
- **振幅和频率解耦**（可以独立调节"多强"和"多快"）

这使得 LRA 能够模拟出丰富的触觉纹理 —— 从轻柔的"滴答"到沉重的"咚"。

### 1.3 HD Haptic / 宽频马达

2020 年代，华为、苹果等厂商进一步推出了**宽频线性马达**（如华为的 X 轴线性马达），支持更宽的频率范围（20-300Hz），配合软件 API 可以产生几乎无限丰富的触感模式。HarmonyOS 的 `vibrator` API 中的 **HD Haptic** 就是利用了这类硬件。

### 1.4 游戏手柄中的双马达

主流游戏手柄（Xbox、PS5 DualSense、Nintendo Switch Pro Controller）通常内置两个振动马达：
- **低频马达（heavy/left）**：较大的偏心块，产生沉闷、厚重的低频振动（爆炸、撞击）
- **高频马达（light/right）**：较小的偏心块，产生清脆、尖锐的高频振动（子弹壳落地、引擎嗡鸣）

PS5 的 **DualSense** 更进一步，使用了 **Voice Coil Actuator（音圈驱动器）**，原理和扬声器几乎相同，能播放任意波形，实现了近乎"触觉音频"的精度。

## 第二章：Audio-to-Haptic —— 用算法"听"到震动

### 2.1 核心思想

Audio-to-Haptic 的本质是：**从音频流中实时提取与触觉相关的特征，映射为振动指令。**

人类对触觉最敏感的频率范围是 **20-80Hz**（与低频声音重叠），而对振动强度的感知遵循类似于听觉的对数曲线。这意味着：

> **低频声音（低音炮的频段）天然就是最好的触觉信号源。**

### 2.2 业界方案

| 方案 | 使用者 | 原理 | 优势 | 局限 |
|------|--------|------|------|------|
| **游戏引擎内置** | Unity / Unreal | 游戏逻辑直接触发振动事件 | 最精确，语义明确 | 需要开发者逐个编排；串流场景不可用 |
| **音频低通 + 包络跟踪** | Razer Nari Ultimate / 各类第三方方案 | LPF 提取低频 → 包络检测器 → 映射 | 简单高效，零延迟 | 对音乐节拍不敏感，无法区分"持续轰鸣"和"鼓点" |
| **Onset Detection** | aubio / librosa / Essentia | FFT + spectral flux → peak-picking | 能精准检测节拍、鼓点 | 计算量较大，有微小延迟 |
| **Apple Core Haptics** | iOS 游戏 | 声明式 AHAP 文件 + 实时参数 | 硬件级优化，触感丰富 | 仅限 Apple 生态 |
| **PS5 DualSense Audio Haptic** | PS5 游戏 | 音圈直接播放经过处理的音频波形 | 触感 = 声音，真正的"摸到声音" | 需要专门硬件 |
| **Android VibrationEffect** | Android 12+ | Composed vibration + 基元组合 | 系统级标准化 | 需要硬件支持，非实时音频驱动 |
| **HarmonyOS HD Haptic** | HarmonyOS 5+ | VibratorPatternBuilder 编程构建波形 | 可控频率+强度+时间 | 需要宽频线性马达设备 |

### 2.3 关键 DSP 概念速览

#### 低通滤波器（Low-Pass Filter）

想象一个声音信号是一杯混合果汁 —— 里面有高音的小提琴（高频）和低沉的鼓声（低频）。低通滤波器就像一个滤网，只让低频分量通过。

在 DSP（数字信号处理）中，最常用的是 **Biquad 滤波器**（二阶 IIR 滤波器），其传递函数为：

$$H(z) = \frac{b_0 + b_1 z^{-1} + b_2 z^{-2}}{1 + a_1 z^{-1} + a_2 z^{-2}}$$

其中系数由截止频率和 Q 值决定。**Butterworth** 类型的 Biquad 提供"最大平坦"的通带响应 —— 截止频率以下的信号几乎无衰减，以上以 -12dB/octave 快速衰减。

#### 包络跟踪器（Envelope Follower）

滤波后的信号仍然是快速震荡的波形。包络跟踪器提取信号的"轮廓"：

```
攻击阶段（Attack）：信号变强时快速跟上  → ~5ms
释放阶段（Release）：信号变弱时缓慢释放  → ~80ms
```

这模拟了人类的触觉感知特性：我们能感受到突然的冲击（拳头打到身上），但震动消退时的感觉更平滑。

#### Onset Detection（起始检测）

对于音乐场景，我们不关心"低音有多强"，而关心"鼓是什么时候敲的"。这就是 onset detection 的任务。

经典的 **Spectral Flux** 方法：
1. 对每帧音频做 FFT（快速傅里叶变换），得到频谱
2. 计算相邻帧频谱的变化量（只取正向变化 = 能量增加的频段）
3. 对变化量进行自适应阈值检测
4. 检测到的峰值就是 onset（音符/鼓点的起始时刻）

### 3.2 游戏/电影模式：感受每一次爆炸

当你在玩射击游戏或看一场动作电影时，重要的是"低频能量有多强"。

**处理管线：**

1. **Butterworth LPF（截止 80Hz）** —— 只保留低音炮频段的信号。为什么是 80Hz？因为人类皮肤的 Pacinian 小体（深压觉感受器）对 40-80Hz 最敏感，恰好与低音炮的频率范围高度重叠。

2. **攻击/释放包络** —— 攻击时间 5ms（快速捕捉枪声起音），释放时间 80ms（自然衰减，不会"咔哒"截断）。

3. **自适应噪声门限** —— 动态追踪环境底噪。游戏不是一直安静的 —— 引擎声、环境音构成了背景噪声。噪声门限确保只有显著高于背景的低频冲击才会触发振动。

4. **RMS 音量权重** —— 如果整体音量很低（比如游戏暂停画面的环境音），即使低频占比高也不应该振动。通过 SmoothStep 函数实现平滑的音量门控。

5. **非线性强度映射** —— `pow(x, 2.5)` 的 gamma 曲线意味着：
   - 小的低频波动（环境轰鸣）→ 几乎感觉不到
   - 中等冲击（远处爆炸）→ 微弱触感
   - 强烈冲击（近距离爆炸/枪声）→ 明显振动

   这符合人类触觉的韦伯-费希纳定律：**感知强度与刺激强度的对数成正比**。

### 3.3 音乐/节奏模式：跟着鼓点脉动

当你玩音乐游戏或听歌时，持续的低频振动反而是干扰。重要的是精准的**节拍同步**。

这里我们采用了 **aubio + 自研能量分析** 的混合方案：

#### aubio 是什么？

[aubio](https://aubio.org) 是一个开源的音频分析库，由 Paul Brossier 在 2003 年作为博士论文项目开始开发，至今已有 20+ 年历史。它在学术界和工业界都被广泛使用（Sonic Visualiser、Ardour 等知名音频软件都有集成）。

**我们使用的 Spectral Flux 方法：**

1. 对每 5ms 的音频帧做 **1024 点 FFT**（窗口是 hop size 的 4 倍，这是标准实践）
2. 计算相邻帧的**频谱正向变化量**（Spectral Flux）
3. 通过 **自适应频谱白化（Adaptive Whitening）** 消除不同频段的能量差异
4. 使用 **Peak-Picking** 算法从 flux 信号中检测峰值
5. 对峰值应用动态阈值和最小间隔（80ms ≈ 每秒最多 12.5 次 onset）

```
原始音频 → FFT → 频谱差分(只取正值) → 自适应白化 → 峰值检测 → onset!
```

#### 为什么不只用 aubio？

aubio 告诉我们 **"什么时候敲了"**，但不告诉我们 **"敲得多重"**。所以我们还需要自己的能量分析来计算振动强度：

```
onset 强度 = f(当前能量 / 背景能量) × 低频加成 × 灵敏度 × 音量权重
```

#### 备用检测器

aubio 基于 FFT，有固有的一帧延迟（~5ms）。对于某些极快的瞬态（比如电子音乐中的合成鼓），我们还有一个零延迟的备用检测器：

- 短窗口 EMA（~80ms）追踪瞬时能量
- 长窗口 EMA（~800ms）追踪背景水平
- 瞬时/背景 > 自适应阈值 → 触发

#### 脉冲衰减

检测到 onset 后，不是简单地"振一下"就结束。我们使用**指数衰减曲线**：

$$I(t) = I_0 \cdot e^{-3(1-t)}$$

从全强度到接近消失经历约 120ms（8 步 × 15ms 节流间隔），模拟真实鼓面的振动衰减。

### 3.4 自动模式：让算法选择

有时候游戏中既有爆炸又有背景音乐。自动模式通过**瞬态密度 + 周期性分析**来判断当前内容类型：

**每 3 秒进行一次评估：**

1. **瞬态密度**：统计时间窗口内能量突变的次数
   - 6-30 次/3秒 → 可能是音乐（鼓点节奏）
   - <6 或 >30 → 可能是游戏（太少=安静场景，太多=混战）

2. **周期性分析**：计算 onset 间隔的**变异系数（CV = 标准差 / 均值）**
   - CV < 0.5 → 间隔规律 → 有节拍 → 音乐
   - CV > 0.5 → 间隔随机 → 游戏音效

3. **滞后保护**：连续 2 次相同判定才真正切换，避免频繁跳变。

这是一种轻量级的音频场景分类方法。相比于基于深度学习的方案（如 YAMNet、AudioSet），它的优势是零模型依赖、零堆分配、毫秒级决策。

### 3.5 振动输出：从数字到物理

分析引擎输出两个值：
- **intensity（0-100）**：应该用多大力去振
- **lowFreqRatio（0-100）**：低频能量在总能量中的占比

#### 手机/平板（设备振动）

在支持 HD Haptic 的华为设备上：

```typescript
// 游戏模式：持续 300ms 的低频连续振动
builder.addContinuousEvent(0, 300, {
    intensity: intensity,           // 强度跟随音频
    frequency: 30 + (intensity/100) * 20,  // 30-50Hz
});

// 音乐模式：短脉冲 60ms
builder.addContinuousEvent(0, 60, {
    frequency: 40 + (intensity/100) * 20,  // 40-60Hz
});
```

不支持 HD Haptic 的设备降级为 `time` 振动（只能控制时长）。

#### USB 手柄

USB 手柄有双马达，lowFreqRatio 正好用来分配：

```
低频马达力度 = intensity × lowFreqRatio
高频马达力度 = intensity × (1 - lowFreqRatio)
```

爆炸时 lowFreqRatio 高 → 低频马达猛烈振动；高频尖锐音效时 lowFreqRatio 低 → 高频马达为主。

#### 智能路由

用户可以选择振动目标：
- **自动**：有 USB 手柄时走手柄，没有时走设备
- **仅手柄** / **仅设备** / **同时**

## 第四章：性能约束 —— 在 5ms 内完成一切

### 4.1 Opus 解码节奏

游戏串流使用 Opus 编码，48kHz 采样率下每帧 240 个样本 = **5ms/帧**。这意味着我们的分析代码必须在 5ms 内完成（否则会阻塞音频播放）。

### 4.2 零堆分配

`BassEnergyAnalyzer` 的所有状态都是内联成员变量，`ProcessFrame()` 中没有任何 `new`、`malloc`、`std::vector` 操作。这消除了 GC 压力和堆碎片。

### 4.3 同线程执行

分析代码在 Opus 解码回调的同一线程中执行，和音频播放串行。这样做的好处：
- **零拷贝**：直接使用解码后的 PCM buffer，不需要额外的线程间通信
- **零延迟**：分析结果即时可用
- **无锁**：不需要 mutex，不存在竞争条件

### 4.4 节流控制

即使每帧都分析，我们也不需要每帧都振动。节流策略：
- 游戏模式：每 20ms 最多回调一次（~50 次/秒）
- 音乐模式：每 15ms 最多回调一次（~66 次/秒）
- 强度变化 < 3 时跳过回调（避免无意义的微调）

### 4.5 aubio 的开销

aubio 的 FFT 运算是整个管线中最重的部分（1024 点 FFT ≈ 5120 次浮点乘加）。但在现代 ARM 处理器上，这大约只需要 **~0.1ms**，远在预算之内。

### 5.1 游戏主机

| 设备 | 技术 | 特点 |

- **Android VibrationEffect Composition**（Android 12+）：基于预定义基元（click、tick、thud）的组合
- **HarmonyOS HD Haptic**（HarmonyOS 5+）：VibratorPatternBuilder 支持自定义频率/强度/时间

### 5.3 穿戴设备与外设

- **Razer Nari Ultimate**：游戏耳机内置触觉驱动器，将低频音频转为头部振动
- **Woojer Vest Edge**：穿戴式触觉背心，多区域独立振动
- **Lofelt Nice Vibrations**：Unity 插件，提供跨平台的音频驱动触觉方案（已被 Meta 收购）

### 5.4 VR/XR

在 VR 场景中，触觉反馈是"存在感"的关键因素。Meta Quest 的手柄使用 LRA 马达，配合手部追踪可以产生"虚拟触碰"的感觉。

### 5.5 串流场景的特殊挑战

在云游戏/串流场景下，Audio-to-Haptic 几乎是**唯一可行的方案**。原因：

1. **无法获取游戏引擎事件** —— 串流客户端只收到编码后的音视频流
2. **协议不包含振动数据** —— Moonlight/GameStream 协议传输手柄输入（含振动）是从主机到客户端的指令，但只覆盖了游戏主动触发的振动
3. **手机/平板没有主机端的振动信息** —— 触屏上根本没有手柄

因此，从音频流中提取触觉信号，是赋予移动设备"体感"的最自然、最通用的方式。

## 第六章：未来展望

### 6.1 AI 驱动的触觉合成

Google Research 在 2022 年发布了 [Caviar](https://research.google/blog/generating-haptic-feedback-for-videos/) 项目，使用 Transformer 模型从视频+音频中生成高质量的触觉信号。Meta Reality Labs 也在探索基于扩散模型的触觉生成。

### 6.2 空间触觉

随着多区域振动马达的普及（如 PS5 的双马达、触觉手套的多指节驱动），未来可以实现**空间化的触觉** —— 让你知道"爆炸发生在左边还是右边"。

### 6.3 标准化

目前各平台的触觉 API 差异巨大（Apple 的 AHAP、Android 的 VibrationEffect、HarmonyOS 的 VibratorPattern），行业需要一个跨平台的触觉描述标准。W3C 的 [Vibration API](https://www.w3.org/TR/vibration/) 是一个起点，但目前只支持最基础的 on/off 控制。

## 结语

音频驱动触觉反馈是一种将"听觉"翻译为"触觉"的技术。它的核心洞见很简单：

> **低频声音和触觉振动，在物理本质上是同一种东西 —— 机械波。只不过一个通过空气传到耳朵，另一个通过固体传到皮肤。**

在 Moonlight 中，我们用一个 Butterworth 低通滤波器、一个包络跟踪器、一个学术级的 onset 检测器（aubio），加上一个场景自动识别引擎，在每帧 5ms 的音频解码间隙里完成了从"听到"到"摸到"的转换。

没有 AI 模型，没有云端推理，就是经典的 DSP —— **数字信号处理，永远优雅。**
